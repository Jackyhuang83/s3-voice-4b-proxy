## 1. Upstream reuse / compatibility justification

- Firmware `78/xiaozhi-esp32 v2.6.0` source `main/ota.cc` accepts custom `wifi.ota_url`, POSTs with `Device-Id` and `Client-Id`; it stores the `websocket.url` returned by OTA.
- Firmware `main/protocols/websocket_protocol.cc` connects to full server-provided URL and sends the same two identity headers and `Authorization` token; no firmware edit/flash required.
- Upstream `xinnan-tech/xiaozhi-esp32-server v0.9.8` `core/api/ota_handler.py` can return configured `server.websocket`. The upstream bearer token verifies on the WebSocket server, but OTA by itself can mint a token to any caller. The `allowed_devices` list skips token verification for listed devices, **NOT** an ingress denylist.
- Use **official Caddy v2.11.7** for exact route/method/header matching + native WS reverse proxy; **official cloudflare/cloudflared 2026.11.0** as a dedicated outbound-only connector, not a custom proxy implementation. Both images are resolved to SHA256 digests on the host before service start.
- Cloudflare docs confirm `cloudflared tunnel run --token-file` requires cloudflared >=2026.10.0; the dedicated token is read from a bind-mounted local file, not placed on CLI, in Git or as a Docker env variable.
- Sources: https://caddyserver.com/docs/caddyfile/matchers ; https://caddyserver.com/docs/caddyfile/directives/reverse_proxy ; https://developers.cloudflare.com/tunnel/reference/run-parameters/ ; https://developers.cloudflare.com/tunnel/get-started/ ; https://developers.cloudflare.com/network/websockets/ .

## 2. Security boundary

Public URL examples (NOT yet active; never share full URL including the secret):
- OTA: `https://voice.cncloudx.com/xiaozhi/ota/<private-256-bit-secret>`
- WS: `wss://voice.cncloudx.com/xiaozhi/v1/<same-private-secret>`

A04 gateway accepts each request only when **all** of the following match: 256-bit path secret, expected HTTP method, exact route, one explicitly enrolled `Device-Id` and `Client-Id` pair. WebSocket additionally requires the protocol upgrade headers; upstream requires a signed bearer token generated by accepted OTA. Caddy rewrites the private public path to the official /xiaozhi/ota/ or /xiaozhi/v1/ upstream route. **All other requests get HTTP 403**. Caddy deliberately discards HTTP access logs so full secret paths are not written to local logs.

**Crucial scope limit:** MAC/UUID headers are spoofable and bearer paths can be replayed if leaked. The URL secret raises admission security substantially without a firmware fork, but it is **not hardware-backed authentication**. Keep private URL and identity file on root-only VPS and 4B NVS, disable external logs that expose request paths, ensure TLS. Avoid opening the hostname to other real users or setting any billable model keys until the A05 API budget/rate controls are validated. This A04 staging uses a **synthetic device identity**, not an actual 4B MAC/UUID. Real device pairing and OTA NVS cutover belong to P3 A07.

Caddy site has NO general-purpose health path, OTA binary download path or public management UI. **Do not** put browser OTP Cloudflare Access in front of this device hostname (firmware cannot complete login); do not mistake the separate F50 owner-email Access policy for device authentication.

## 3. Network / firewall — no new public inbound ports

| Port | Direction | Transport | Owner / action |
|---|---|---|---|
| 18000 | Host loopback | TCP | Existing A03 WS, remain loopback |
| 18003 | Host loopback | TCP | Existing A03 OTA, remain loopback |
| 18080 | Host loopback | TCP | New A04 Caddy gateway, remain loopback |
| 443 | Cloudflare edge | TCP | Public WSS/HTTPS handled by Cloudflare; **NO NEW VPS inbound rule** |
| 7844 | VPS outbound | UDP (QUIC) or TCP (HTTP/2) | For dedicated Cloudflare Tunnel; check only if VPS restricts outbound |
| 80/443/8080/12333/28888 | Existing services | existing | Do not modify or replace |

**Verified upstream-image compatibility detail:** The official Caddy 2.11.7 binary is marked with the Linux `cap_net_bind_service=+ep` file capability. A test with every container capability dropped caused `exec /usr/bin/caddy: operation not permitted`. The gateway therefore drops all default capabilities then adds back **only** `NET_BIND_SERVICE`, retaining `no-new-privileges`, non-root UID, read-only filesystem and port 8080. The separate cloudflared connector adds no capabilities.

Caddy and cloudflared share A04's **front** Docker bridge; only Caddy joins existing `s3-voice-ai_default` backend network. No host networking. The cloudflared origin URL in Cloudflare dashboard must be **`http://gateway:8080`**, not localhost and not the HomeSphere Caddy port, because the cloudflared process is in its own Docker bridge. The host mapping 127.0.0.1:18080 is for local tests only.

## 4. Implementation / commands and evidence boundaries

Files:
- `deploy/ai/a04/Caddyfile.in` — exact credentials and route matching, denied paths, native WebSocket proxy
- `deploy/ai/a04/docker-compose.yml` — immutable Caddy/Tunnel images after host resolution, rootless processes, no host network, memory/CPU caps, localhost 18080
- `tools/ai/a04-edge.sh` — stage, local, connect, public, status, rollback; does not modify firewall/DNS
- `tests/ai/a04_gateway_smoke.py` — stdlib HTTP + real WebSocket upgrade/v1 Hello checks; no API billing, no device flash

**A04 stage (on Debian 13 VPS, after final PR CI and exact commit review):**

~~~bash
git -C /tmp/s3-voice-a03-src fetch --depth 1 origin ai/p1-a04-gateway-20261122
git -C /tmp/s3-voice-a03-src checkout --detach FETCH_HEAD
cd /tmp/s3-voice-a03-src
bash tools/ai/a04-edge.sh stage
~~~

Formal run should verify `git rev-parse HEAD` equals the reviewed final CI head SHA. The script refuses stage if A03 is absent, public 18080 occupied, unexpected firmware binaries, upstream auth disabled, or placeholder no-billing keys removed. It backs up A03's exact config then launches a separate Caddy gateway, sets a **synthetic** 4B identity and a fresh random 256-bit bearer path privately, restarts **only** the A03 server to change the WS URL, tests OTA and WS gate, and compares existing running-container names. It retains all private config and backup under root-only paths.

**A04 Cloudflare UI — manual account step only, no connector authorization currently accessible:** Create a **new** remotely managed Cloudflare Tunnel, e.g. `s3-voice-ai`, without touching the existing MiniProbe/F50 tunnels. Under Public Hostname / Published Applications, assign `voice.cncloudx.com` with HTTP service origin `http://gateway:8080` (same Docker bridge). Do not enable browser-based Access OTP. Copy the new Tunnel **token** only into the secure **VPS root-shell prompt** below; NEVER paste it in GitHub, ChatGPT or logs.

~~~bash
cd /tmp/s3-voice-a03-src
bash tools/ai/a04-edge.sh connect
bash tools/ai/a04-edge.sh public
~~~

`connect` reads the token without terminal echo, pins the official cloudflared SHA256 digest, starts only the A04 Tunnel container. It does **not** open any inbound VPS port, modify Cloudflare account or route, or touch existing tunnels. The `public` probe must succeed through real Cloudflare HTTPS and WebSocket, testing a legitimate synthetic identity, wrong IDs, wrong bearer route, forbidden OTA binary path, empty firmware URL, HTTPS certificate and WSS upgrade. A valid gateway does not imply the real 4B has connected.

A04 local checks: `bash tools/ai/a04-edge.sh status`. A04 fail-safe scoped rollback: `bash tools/ai/a04-edge.sh rollback` restores saved A03 `data/.config.yaml`, restarts only `s3-voice-ai-server`, stops only `s3-voice-ai-gateway` and `s3-voice-ai-tunnel`. The original HomeSphere, MiniProbe, and their Caddy/Tunnel remain untouched. Do not repeat `stage` after partial failure without inspecting preserved backup state.

**Do not expose real LLM keys in A04.** Provider vendor hard spending limits/alerts, ASR/TTS billing and model selection belong to A05/A06.
